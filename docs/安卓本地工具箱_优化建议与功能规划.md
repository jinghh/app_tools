## 一、现有功能可优化项

### P0 正确性问题（建议尽快修）

#### 1. `allowBackup` 与 Cookie 隐私承诺冲突 ✅

- **问题**：`AndroidManifest.xml` 中 `android:allowBackup="true"`，而
  `CookieStore` 把各平台登录 Cookie 存在 `filesDir/cookies/` 下，并承诺
  「仅保存在应用私有目录，不外传」。开启备份意味着这些 Cookie 会随系统云备份 /
  `adb backup` 离开设备——小红书、微博的会话凭证进入云备份，违背 PRD 7 隐私承诺。
- **位置**：`AndroidManifest.xml`（application 标签）、`download/CookieStore.kt`。
- **建议**：`allowBackup="false"`；若希望保留其他数据的备份能力，则改为
  `fullBackupContent` / `dataExtractionRules` 并显式排除 `cookies/` 目录。
  注意：若后续把下载产物移入 `filesDir`（见第 2 条），大体积媒体也应一并排除出备份。
- **验收**：配置后用 `adb backup` / 云备份验证 Cookie 目录不再被导出。

#### 2. 下载成品放在 `cacheDir`，可能被系统回收 ✅

- **问题**：`YtDlpDownloader.outDir()` 把产物放在 `cacheDir/ytdlp-downloads/`。
  `cacheDir` 在磁盘紧张时可被系统直接清空，用户下载完成后若未及时「保存到本地」，
  文件会无声丢失。
- **位置**：`download/YtDlpDownloader.kt`（`outDir`、`Downloaded` 事件处理）。
- **建议**：下载成功后把成品从 `cacheDir` 转移到 `filesDir/downloads/`（或
  `getExternalFilesDir()`）；`.part` 半成品可继续留在 `cacheDir`（丢了可重下）。
  转移时同步更新 `DownloadUiState.file` 指向新路径。
  该改造同时是「下载历史」功能的数据基础（见二、新功能 3）。
- **验收**：下载完成后杀进程再进 App，成品仍在；系统「清理缓存」不再影响成品。

### P1 可靠性

#### 3. 转 GIF / GIF 压缩任务：无后台保护、状态为界面级 ⬜

- **问题**：下载模块专门用 `DownloadCenter`（进程级单例）+ 前台服务对抗
  Cached Apps Freezer，但 GIF 两个页面的任务状态全部是
  `remember { mutableStateOf(...) }`（`ui/GifToolScreen.kt`、`ui/GifCompressScreen.kt`）：
  - 旋转屏幕 / 界面重建后 UI 回到空闲态，而 FFmpeg 仍在后台跑，结果对不上号；
  - 退后台久了进程被冻结（编码停摆）甚至被回收（任务丢失）。
- **建议**：照 `DownloadCenter` 的模式建进程级任务单例（如 `MediaJobCenter`），
  长任务期间复用前台服务（`dataSync` 类型同样适用于编码）。
  顺带把 `FfmpegRunner` 「`FFmpegKit.cancel()` 是进程级、全局同时只允许一个会话」
  的隐式约束在单例里显式化（排队或拒绝并发）。
- **验收**：转换中旋转屏幕状态不丢；转换中切后台 5 分钟回前台任务仍在推进。

#### 4. 进程被杀后下载不会自动恢复 ✅（代码已实现，START_STICKY 系统重启豁免待真机验证）

- **问题**：`DownloadService` 返回 `START_NOT_STICKY`，注释依据是「当前 yt-dlp 路径无法续传，
  重启无意义」——该前提在 v0.1.5 加入断点续传后已不成立。现在进程被杀后 `.part` 残留与
  续传 URL 均已持久化，但恢复完全靠人工：必须打开 App、切到下载页、手动点「继续下载」。
- **位置**：`download/DownloadService.kt`（`onStartCommand`）、`download/DownloadCenter.kt`
  （类注释中「无法续传」的固有限制说明需同步改写）、`download/YtDlpDownloader.kt`
  （`partialBytes` / `resumeUrl` 已具备，直接复用）。
- **建议**：改 `START_STICKY`；服务被系统重启（`onStartCommand` intent 为 null）时检测
  「存在 `.part` 残留 + 记录的续传 URL」→ 以 resume=true 自动续传（跑在前台服务里，
  进度通知可见，不会无感耗流量）。**需真机验证**：Android 12+ 限制后台启动前台服务，
  需确认「系统重启 sticky 服务」不受该限制；若受限，退化为「打开 App 进入下载页时
  检测到残留且非 RUNNING 即自动续传」。
- **验收**：下载中 `adb shell am kill` 杀进程，无人干预下载自动续传至完成（或打开 App 即续传）。

#### 5. 网络抖动类失败不自动重试 ✅

- **问题**：下载失败后全部依赖手动重试。`YtDlpDownloader.friendlyMessage` 已把失败分成
  「链路问题（连接被拒/重置/超时/DNS）」与「链接本身问题（404/登录/限流）」，其中链路类
  失败重试价值最高——且 v0.1.5 的续传能力让重试不必从头下载。
- **位置**：`download/DownloadCenter.kt`（`handleEvent` 的 Failure 分支）、
  `download/YtDlpDownloader.kt`（错误分类已就绪）。
- **建议**：失败时若命中链路类错误，自动以 resume=true 用同一 URL 重试 1–2 次（加短暂退避），
  仍失败才落为 FAILED 并照常提示；限流（429）/登录类错误**不重试**，避免火上浇油。
  与 P1-4 共用「同一 URL + resume」的自动恢复逻辑。
- **验收**：下载中短暂断网再恢复，无人工干预自动续传完成；限流错误仍只提示不重试。

## 三、建议落地顺序

1. **先修再建**：P0-1（allowBackup 隐私修复）+ P0-2（产物移出 cacheDir）——
   两者都是正确性问题，改动小、风险低、收益明确。
2. **第一波功能**（均在现有框架内，一两轮迭代可出）：
   视频压缩（带「微信 25MB」预设）、片段导出 mp4、下载历史、剪贴板/分享直达（P2-4/5）。
3. **第二波**：P1-3（GIF 任务进程级化 + 后台保护）、GIF 转视频、存储清理卡片。
4. **第三波**（结构性投入）：PRD 阶段 3 固定工作流、自研 X 解析器——
   前者把 App 从「三个工具」变成「一条流水线」，后者一次清掉下载模块的三个已知限制
   （不可取消 / 无清晰度选择 / 文件名不友好，见 README「已知限制」1、2 条）。

> 补充（同日对话评审）：另一候选顺序是先打包一个「收尾包」发 v0.1.6——
> P1-4（进程被杀自动续传）+ P2-11（参数记忆）+ P2-9（存储清理）+ P3-17（过时表述清理），
> 可捎上 P1-5（网络失败自动重试）——全是小改动，但能让现有功能明显更成品，
> 再投入第二、三波的结构性工作。
