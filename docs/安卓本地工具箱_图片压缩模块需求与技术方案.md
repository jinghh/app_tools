## 1. 背景与目标

### 1.1 背景

现有工具箱已具备「视频下载 → 视频转 GIF → GIF 压缩 → 视频压缩」四步，压缩类模块的统一范式是
**「参数级联 + 真实字节数校验、达标即停、绝不覆盖原图」**（见 `gif/GifCompressor.kt`、
`video/VideoCompressor.kt`）。

使用者在日常中最常见的诉求其实是**图片**：微信发图九宫格限流、论坛上传限 2MB、
截图/照片需要转格式或改尺寸。这是一个使用频率高于视频/GIF 的场景，且当前完全没有入口。

### 1.2 目标

新增一个独立的**图片压缩模块**，在一次操作中覆盖四个诉求：

1. **有损压缩**：按质量 q 压缩 JPEG / WebP；
2. **无损压缩**：像素不变的重新编码（PNG / WebP 无损）；
3. **尺寸调整**：按长边、百分比或自定义宽高缩放（只缩不放）；
4. **格式转换**：JPEG / PNG / WebP 互转，正确处理透明通道与 EXIF 方向。

支持**批量多选**（串行处理），结果可一键保存到相册。

### 1.3 设计原则

- **零新增依赖**：全部使用 Android 平台原生 `Bitmap` / `BitmapFactory` / `ExifInterface` / `MediaStore`；
- **复用既有范式**：事件模型、结果模型、日志卡、参数记忆、SAF 导入、AppStorage 清理全部对齐现有模块；
- **对用户诚实**：无损压缩的真实收益（通常 0–15%）必须在界面上说明，不制造"一键减半"的错误预期；
- **原图只读**：任何模式下原文件字节不变。

### 2.2 本期不做（明确排除）

| 项 | 排除理由 |
|---|---|
| 动图（GIF / 动图 WebP / AVIF）压缩 | GIF 已有独立模块；动图 WebP 平台侧只有解码器，无编码器（见优化建议文档新功能 9 的实测结论） |
| PNG 颜色量化有损压缩 | ffmpeg 的 png 编码器不支持 `pal8`，Android 无量化 API；自研量化成本与收益不匹配 |
| HEIF/HEIC **输出** | 平台无编码 API；HEIC **输入**支持（API 28+ 解码后转 JPEG/WebP） |
| JPEG 字节级剥元数据 | 收益普遍 <1%，且存在方向翻转毁图风险，详见第 13 节决策记录 D4 |

| 批量「另存为」到指定目录 | 需 SAF 目录树授权（`OpenDocumentTree`），M3 再做 |

## 3. 用户场景与主流程

### 3.1 典型场景

1. 手机相册里的 12MP 照片要发微信，原图 4MB，需要压到 1MB 以内且长边不超过 1920；
2. 设计师给的 PNG 截图 3MB，论坛只收 JPG，需要转格式 + 压到 500KB；
3. 一批 20 张截图需要统一转 WebP 并缩到 50%，逐张处理太慢；
4. 需要严格控制在目标大小内（如投递系统限 200KB）。

### 3.2 主流程

1. 进入「图片」页签 → 点「选择图片」→ 系统文件选择器（可多选）；
2. 选中文件复制到 `cacheDir/image-input/`，逐张探测元信息（大小/宽高/格式/alpha/EXIF/是否动图）；
3. 配置参数：压缩模式 → 质量或目标大小 → 尺寸 → 输出格式（实时展示预估输出尺寸）；
4. 点「开始压缩」，批量串行执行，逐张上报「第 n/N 张 · 当前阶段」；
5. 结束后展示结果列表 + 汇总（共 N 张，成功 M 张，总节省 X MB / Y%）；
6. 点「保存到相册」逐张写入 MediaStore；单张时另有「另存为」。

## 4. 功能需求

### FR-1 导入

- 使用 `ActivityResultContracts.OpenDocument`，mime 过滤 `image/*`，支持多选；
- 复用 `ui/FileUtils.kt` 的 `copyUriToCache(context, uri, "image-input", "jpg")` 与 `sanitizeFileName`；
- 导入后对每张探测并展示：

| 字段 | 获取方式 |
|---|---|
| 文件大小 | `File.length()` |
| 宽 × 高 | `BitmapFactory.Options(inJustDecodeBounds = true)` |
| 格式 | `outMimeType` 映射（jpeg/png/webp/heic/gif） |
| 透明通道 | 解码后 `Bitmap.hasAlpha()`（PNG/WebP 需要，JPEG 恒 false） |
| EXIF 方向 | `android.media.ExifInterface(file)` 的 `TAG_ORIENTATION` |
| 是否动图 | GIF 一律视为动图；WebP 检查 `outMimeType == image/webp` 且文件含 `ANIM` chunk（可选，M2） |

- **拒绝清单**（逐张判定，不阻断整批）：
  - `image/gif` → 提示「动图请使用 GIF 压缩页」；
  - 解码失败 / `outWidth <= 0` → 「无法识别的图片」；
  - 总像素 > 1 亿（100MP）→ 「图片过大，暂不支持」。

### FR-2 压缩模式

界面用三个分段按钮切换，同一时刻只有一种生效：

| 模式 | 输入 | 行为 |
|---|---|---|
| **有损** | 质量滑块 1–100（快捷档：高 85 / 中 75 / 低 60） | 输出格式为 JPEG 或 WebP 时 q 生效；若输出格式为 PNG，提示「PNG 为无损格式，质量参数无效」并回落到无损逻辑 |
| **无损** | 无参数 | **原格式 + 原始尺寸时直接复制原文件（不重编码，体积不变）**；换尺寸/换格式时才重编码为 PNG 或 WebP 无损（后者仅 API 30+）；输出格式显式选 JPEG 时拦截并提示「JPEG 不支持无损重编码」 |
| **目标大小** | 目标大小滑块（KB，上限=最大那张原图，下限固定 10KB） | 见 5.5 的搜索策略，自动选择参数组合 |

**数值参数的交互约定（v0.2.0 起）**：质量、目标大小一律用**滑块拖动**，不使用输入框。
理由是这类参数本质是「大致范围」：输入框要弹键盘、要处理空值与非法字符、要额外配预设才好用；
滑块一拖即得，且滑块下方固定显示「原始 X / 设置 Y」两行对照，用户不必自己心算
「设成 3MB 到底算不算小」。

**滑块区间（2026-11-04 调整）**：上限随载入文件收缩到原图大小，避免「设置值比原文件还大」的假设置；
**下限改为固定 10KB 绝对值**，不再按原图的 5% 计算。原因是 5% 护栏与「输出尺寸」脱节：
用户把长边缩到 640px 后像素数可能只剩 1/10，实际 20–30KB 就够，却被 52KB 之类的下限挡住。
现在能否达标完全交给引擎（走完阶梯仍超限会明确标注 `metTarget=false`），
界面额外显示「当前目标约为原图的 X%」，低于 2% 时用红字提示「多数图片无法达标、产物可能明显模糊」。
同一套滑块组件（`ui/CommonUi.kt` 的 `ParamSlider`）也用于视频压缩与 GIF 压缩的目标大小，
保证三个压缩页手感一致。

**文案要求（写进界面）**：无损模式下固定展示一行说明——
「无损压缩只重编码、不改像素，体积通常只能减小 0–15%（原图已被优化过时可能无变化）。如需显著减小体积，请用有损或转 WebP。」

### FR-3 尺寸调整

- 选项：保持原始 / 长边 2048 / 1920 / 1280 / 1080 / 640 / 百分比 75% / 50% / 25% / 自定义；
- 自定义时锁定宽高比，只填长边或宽高任一；换算按 `round` 取整，且保证最短边 ≥ 1；
- **只缩不放**：目标尺寸 ≥ 原尺寸时不放大，直接保持原始尺寸，并在界面标注「已跳过（不放大）」；
- 缩放前必须先应用 EXIF 焦点方向（先旋转再缩放，否则输出方向错乱）；
- 预估输出尺寸即时显示（如 `1920 × 1440`）。

### FR-4 格式转换

- 输出格式选项：保持原格式 / JPEG / PNG / WebP；
- 保持原格式时：JPEG→JPEG、PNG→PNG、WebP→WebP（有损源保持有损），HEIC→JPEG（无法回写 HEIC）；
- **透明通道规则**：源图 `hasAlpha()` 且输出为 JPEG 时，先把 alpha 合成到白色底再编码；
  界面提示「透明背景将填充为白色」；
- 输出扩展名与 mime 严格对应：`.jpg` / `.png` / `.webp`；
- 文件名：`${原文件名主干}_${宽}x${高}.${ext}`，同名冲突追加 `_1`、`_2`；**绝不覆盖原图**。

### FR-5 批量执行

- **严格串行**：一个张处理完再处理下一张（并行解码 3 张 12MP 图 ≈ 144MB，必 OOM）；
- 单张失败不中断整批：记录失败原因，继续下一张；
- 进度：`第 n/N 张 · <阶段>`，阶段枚举 `解码 → 缩放 → 编码 → 校验`，**不做百分比假进度**
  （单张耗时通常 100–500ms，百分比会闪跳）；
- 取消：点击「取消」后，当前张处理完（不可中断）即停止，剩余张标为「已取消」；
- 汇总：成功数 / 失败数 / 原始总字节 / 输出总字节 / 总节省比例 / 总耗时。

### FR-6 结果与保存

- 结果卡片逐张展示：文件名、输出尺寸、输出大小（原 x → 现 y，降幅 z%）、参数标签、耗时；
  未达标项标红提示「未达标，已保留最低参数下的最佳结果」；
- **保存到相册**：`MediaStore.Images`，`RELATIVE_PATH = Pictures/MyAppTools`；
- **另存为**（仅单张）：`CreateDocument` + 对应 mime；
- 保存结果用 Toast + 日志反馈，失败不静默。

### FR-7 参数记忆

新增 `image/ImageToolPrefs.kt`（照 `gif/GifToolPrefs.kt` 模式）：
记住**压缩模式、质量、目标大小、输出尺寸预设、自定义长边、输出格式**，进页面恢复上次值。
质量和目标大小改为滑块后存的是 Float 字符串（`80.0` / `500.0`），读取用 `toFloatOrNull()`
并夹回合法区间，因此能兼容旧版输入框留下的纯数字（`80` / `500`）；自定义长边仍是文本输入。

### FR-8 页面入口

- 底部栏新增第 5 项：标签「图片」，图标 `Icons.Filled.Image`；
- `MainActivity` 增加 `TAB_IMAGE = 4` 与对应 `when` 分支；
- 5 项时中文标签易被挤压，`NavigationBarItem` 的 label 加 `maxLines = 1`、`softWrap = false`。

### FR-9 与既有模块的关系

- 本期**不做**跨页直传（图片产物不需要送进转 GIF / 视频压缩）；
- 但 `image-output` 需纳入 `AppStorage` 的存储统计与一键清理。

## 5. 技术方案

### 5.1 为什么不用 FFmpeg（证据链）

| 事实 | 来源 | 结论 |
|---|---|---|
| APK 内 `libavcodec.so` 有 webp **解码器**、无 libwebp **编码器** | 优化建议文档新功能 9（2026-10-28 实测） | ffmpeg 无法输出 WebP，而 WebP 是图片减体积的主力 |
| `ffmpeg-kit-min` 图片编码器仅 `mjpeg` / `png`，且 png 不支持 `pal8` | 同文档 + 编码器清单核实 | 无法做调色板 PNG（即无法做 PNG 有损） |
| `Bitmap.compress()` 原生支持 JPEG / PNG / WebP，无临时文件、无进程间拷贝 | Android SDK | 单张 12MP 图 100–500ms，快于 ffmpeg 一个数量级 |

**结论**：图片模块**完全不依赖** `gif/FfmpegRunner.kt`，避免无谓的解封装/重封装与临时文件管理。

### 5.2 包结构

```
app/src/main/java/com/jhh/myapptools/
├── image/
│   ├── ImageCompressor.kt   # 引擎：解码 → 缩放 → 编码 → 校验；批量串行调度
│   ├── ImageInspector.kt    # 元信息探测（尺寸/格式/alpha/EXIF/动图/体积）
│   ├── ImageFormat.kt       # 输出格式枚举与 API 能力判定（WebP 无损等）
│   └── ImageToolPrefs.kt    # 参数记忆
└── ui/
    └── ImageCompressScreen.kt  # 页面（复用 ScreenScaffold + Card 布局）
```

事件与结果模型（与 `VideoCompressEvent` 同构）：

- `ImageCompressEvent`：`BatchStart(total)` / `ItemStart(index, total, name)` / `ItemStage(index, stage)` /
  `ItemDone(index, result)` / `ItemFailed(index, name, reason)` / `BatchDone(summary)` / `Cancelled`
- `ImageCompressResult`：`file` / `originalBytes` / `outputBytes` / `srcWidth×srcHeight` /
  `outWidth×outHeight` / `format` / `quality` / `mode` / `finalLabel` / `metTarget` / `elapsedMs`
- `ImageCompressOptions`：`mode` / `quality` / `targetBytes` / `maxEdge` / `scale` / `customWidth×Height` / `outputFormat`

### 5.3 解码与内存策略（第一优先级）

1. **先探边界**：`BitmapFactory.Options(inJustDecodeBounds = true)` 拿 `outWidth × outHeight`；
2. **算采样率**：`inSampleSize` 取 2 的幂，使 `max(outWidth, outHeight) / inSampleSize >= 目标长边 * 2`
   （粗降到目标 2 倍以内），避免一次性解码 100MP 图；
3. **精缩放**：`Bitmap.createScaledBitmap(src, tw, th, /* filter = */ true)`；
4. **内存预算兜底**：只按目标尺寸算采样率是不够的——用户选「保持原始尺寸」时采样率会是 1，
   等于整图解码（50MP 图 ARGB_8888 需 200MB）。因此再用 `maxMemory / 4` 作为单张解码预算，
   按 `宽/采样 × 高/采样 × 4` 估算，超预算就继续加倍 `inSampleSize`（上限 64），
   宁可降清晰度也不让整批崩掉；
5. **统一用 `BitmapFactory`，不用 `ImageDecoder`**：后者默认返回 `HARDWARE` 配置位图，
   `createScaledBitmap` / `getPixels` / 合成白底时会踩兼容问题，且无法复用；
6. **必须捕获 `OutOfMemoryError`**：OOM 是 `Error` 不是 `Exception`，
   现有 `VideoCompressScreen` 的 `catch (e: Exception)` 捕不到。
   图片模块的批量循环需 `catch (t: Throwable)`（并重抛 `CancellationException`），
   把 OOM 转成「单张失败：内存不足（建议降低尺寸）」而不崩溃整个批次。

解码后立即释放引用：`src.recycle()`（非共享位图时）或至少让局部变量出作用域，避免批量累积。

### 5.4 编码能力矩阵（minSdk 24，必须落到实现分支）

| 输出格式 | 有损 | 无损 | API 约束 |
|---|---|---|---|
| JPEG | ✅ quality 0–100 | ❌（JPEG 无无损重编码） | 无 alpha；Android 转码不写 EXIF |
| PNG | ❌（quality 被 Skia 忽略） | ✅ 始终无损 | 全版本 |
| WebP 有损 | ✅ | — | API 24+ 用 `CompressFormat.WEBP`；API 30+ 用 `WEBP_LOSSY` |
| WebP 无损 | — | ✅ | **仅 API 30+ `WEBP_LOSSLESS`**；24–29 无能力，需降级为 PNG 并提示 |

**降级规则**：API < 30 且用户选了「无损 + WebP」→ 自动改 PNG，并提示
「当前系统不支持 WebP 无损编码，已改用 PNG」。

### 5.5 参数级联与目标大小搜索

#### 有损 / 无损模式

单次编码，无级联；只做一次真实字节数校验（用于展示降幅）。

#### 目标大小模式

图片编码极快，用**二分搜索**比线性阶梯更优（最坏 7 次编码即可收敛到 ±3%）：

1. **估算起点**：`ratio = targetBytes / originalBytes`，
   - `ratio >= 1` → 直接返回 q90 结果并提示「目标不小于原图」；
   - 经验映射 `q ≈ clamp(round(ratio * 100 * 1.15), 10, 95)`；
2. **二分**：下界 5、上界 95，每次编码后比较真实字节数：
   - 结果 > 目标 → 上界 = q - 1；
   - 结果 ≤ 目标 → 记录为候选，下界 = q + 1；
   - 终止条件：区间收敛（`hi - lo < 3`）或达到次数上限 7 次；
3. **阶梯兜底**（q 已到 5 仍超限时，按顺序尝试）：
   - 长边降 0.8 倍 → 再 0.6 倍（每次重新二分，最多 2 轮）；
   - 若当前输出是 PNG（无损无法降 q）→ 直接跳尺寸阶梯，并在结果里标注
     「PNG 无损无法靠质量降体积，建议改用 WebP 有损」；
   - 若当前输出是 PNG 且仍超限 → 允许一次「转 WebP 有损 q75」兜底（需在界面上标注已改格式）；
4. 走完阶梯仍超限 → 保留体积最小的那次结果，`metTarget = false`。

**实际参数**：质量二分区间 5–95，每档最多 6 轮；尺寸阶梯 1.0 / 0.8 / 0.65（每档都从缩放后的基准图重新缩，
不在上一档结果上继续缩，避免累积模糊）；单张最多 12 次编码（约 1–3 秒），超出即停，
避免大图批量时无限耗时。所有候选文件写在批次目录、按真实字节数比较，
达标后保留最优者并删除其余候选。

### 5.6 EXIF、色彩与元数据

| 项 | 处理 |
|---|---|
| 方向 | 读取 `TAG_ORIENTATION`；任何重编码都要先物理转正（`Matrix` 旋转/镜像），否则输出方向错乱 |
| EXIF 保留 | `Bitmap.compress()` 不写 EXIF → 拍摄时间/GPS/机型全部丢失。**界面上如实说明**；隐私上是优点 |
| 时间戳 | 若需要保留「拍摄时间」，M2 用 `ExifInterface` 回写 `TAG_DATETIME_ORIGINAL`（可选） |
| 色彩空间 | 广色域（Display P3）图直接转 sRGB 编码可能轻微色偏；M1 按原色域解码，**列入真机验证项**（V3），必要时增加「按 sRGB 解码」开关 |
| ICC | 不承诺保留；转 WebP/JPEG 时由 Skia 决定是否内嵌，不写入需求 |

### 5.7 透明通道合成

源 `hasAlpha()` 且输出 JPEG 时：

1. 新建 `Bitmap.createBitmap(w, h, ARGB_8888)`；
2. `Canvas` 填充白色（`drawColor(Color.WHITE)`）；
3. `drawBitmap(src, 0f, 0f, paint)`（paint 关闭抗锯齿以外的特殊 filter）；
4. 用合成后的图编码 JPEG，用完后 `recycle()` 临时位图。

**不处理会得到黑底**，这是最常见的图片转格式 bug，必须进验收用例。

### 5.8 批量调度与取消

- 串行 `for (input in inputs)`，每张之前检查 `currentCoroutineContext().ensureActive()`；
- 单张内部不可中断（编码 <1s），取消只在张与张之间生效，界面上如实说明「当前张处理完即停止」；
- 所有产物写入**批次目录** `cacheDir/image-output/batch_<时间戳>/`，
  批开始前清理更早的批次目录（最多保留 1 个），批取消时删除本次目录。

### 5.9 进度与耗时

- 阶段枚举驱动，不做假百分比；
- 记录每张 `elapsedMs` 与批次总耗时，展示在结果卡。

### 5.10 防止「越压越大」（2026-11-04 真机反馈后补）

真机复现：2MB 图片选「无损 + 原始尺寸 + 原格式」，输出十几 MB。根因两条：

1. `ImageFormat.losslessTarget()` 对 JPEG 返回 PNG（JPEG 无无损编码能力），
   照片类 JPEG → PNG 通常膨胀 5–10 倍；
2. 即便源是 PNG，若是调色板/8-bit 索引图，解码成 `ARGB_8888` 再编码也会膨胀数倍。

修复（引擎 `ImageCompressor.processOne`）：

- **快路径**：`无损 && 未显式换格式 && 目标尺寸 == 原显示尺寸` →
  直接 `copyTo` 原文件到批次目录，标注「无损 · 原样保留（未重编码）」，
  零 CPU、零膨胀、字节完全一致；
- **通用兜底**：任何模式下，只要用户没改尺寸/格式，且重编码结果 ≥ 原图字节数，
  就删除重编码产物并回退到原图副本，避免有损 q100 / 目标大小给太宽时同样翻车；
- 结果模型新增 `Encoded.format` 记录文件**真实**格式，避免"请求 PNG、实际是 JPEG 副本"时
  保存相册用错 mime。

界面侧同步：

- 无损提示文案改为「原图即最优、体积不变」，不再承诺 0–15% 的收益；
- `无损 + JPEG/WebP 有损源 + 改尺寸/换格式` 用红字警告，并在 `buildOptions` 直接拦截
  「有损源 + 保持原格式 + 改尺寸」这一组合，提示改用有损或显式选输出格式。

| 场景 | 处理 |
|---|---|
| 动图 GIF 导入 | 拒绝单张，提示走 GIF 压缩页 |

## 13. 决策记录

| # | 决策点 | 结论 | 依据 |
|---|---|---|---|
| D1 | 首版是否支持批量 | **支持批量多选**（串行） | 截图/相册批量处理是高频场景，成本约 +40% |
| D2 | 入口位置 | **底部栏第 5 项** | Material3 NavigationBar 上限 5 项，改动最小，不重构现有导航 |
| D3 | 默认保存位置 | **相册**（MediaStore.Images / Pictures） | 图片的使用直觉是"相册里能选到"，视频模块的「下载目录」不符合图片场景 |
| D4 | 「无损压缩」深度 | **只做重编码 + 如实提示**；不做 JPEG 字节级剥元数据 | 见下方量化分析 |

### D4 详情：为什么不做 JPEG 剥元数据

| 源图类型 | 剥离 EXIF/XMP/ICC 后可省 | 占比 |
|---|---|---|
| 手机直出 4MB 照片 | 10–40 KB | 0.3%–1% |
| 微信/QQ 转发过的图 | ≈ 0 | 0%（早已被剥离） |
| 截图 / 网页保存 | ≈ 0 | 0% |
| 设计师 P3 广色域图 | 100–500 KB | 3%–10% |
| AI 绘图输出 | 10–30 KB | 1%–3% |

**弊端**：
1. **方向翻转风险**：`Orientation` 删除后竖拍图横躺；要修正只能重编码，而重编码即有损 —— 与「无损」承诺自相矛盾；
2. 需自写 JPEG 段解析器（约 200 行），`SOS` 之后不得触碰任何字节，非标准 JPEG 上的 bug 极难发现；
3. 剥离 ICC 会掉色（广色域图），此时已不算无损，还需额外开关；
4. 丢失拍摄时间/GPS，影响归档场景；
5. 期望管理灾难：用户点「无损」期待减半，实测 0.8%。

**关键反驳**：`Bitmap.compress()` 天然不写 EXIF，**只要走有损或转 WebP，元数据自动被剥离**，
不需要一行解析器。剥元数据能覆盖的唯一场景是「不愿损失画质、只想再省一点点」，需求频率极低。

**结论**：本期不做；M3 若仍有需求，作为独立开关「移除位置/拍摄信息（不影响画质）」实现，默认关闭。

## 14. 附录：无损模式对用户的说明文案

> **无损 + 原格式 + 原始尺寸 = 原图本身就是最优结果，直接保留，体积不变。**
> Android 平台没有 oxipng / zopfli 级的无损再优化能力；重编码非但不会变小，
> 还常会显著变大（JPEG → PNG 约 5–10 倍，调色板 PNG → ARGB_8888 数倍）。
> 想要明显变小，请选「有损」调低质量，或用「目标大小」自动搜索（会转 WebP / 降尺寸）。

> **2026-11-04 真机反馈修正（v0.2.0 补丁）**：初版在「无损 + 原格式 + 原始尺寸」
> 处理 2MB JPEG 时，因 `losslessTarget()` 把 JPEG 静默改成 PNG，输出膨胀到十几 MB。
> 修复见 5.10；同时补充了「无损 + 有损源 + 改尺寸」的界面拦截，避免换个组合再踩同一个坑。
